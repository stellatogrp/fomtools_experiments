# Portfolio rebalancing through CVXPYgen: solve time vs. number of assets

The analogue of Fig. 4 of the CVXPYgen paper (Schaller et al.), on **our**
portfolio rebalancing problem (`portfolio/`, paper §6.4), with an extra arm:
the solver generated by the fomtools CVXPYgen front end
(`fomtools.cvxpygen.generate_solver`, paper §5.3). Only N = 10 is verified
(`portfolio/results/run_002`); larger N use code generation alone.

## Problem

`model.py` builds the run_002 instance (drift 0.15, z̄ = 0.3, otherwise
`conf/experiment/portfolio.yaml`) for any N through `cluster_run.make_problem`,
modeled in CVXPY with the current holdings as a parameter:

```
minimize  (kappa/2) z' Sigma z - mu' z + lambd ||z - x||_1
s.t.      1'z = 1,  0 <= z <= z_bar
```

`x` enters only the canonical inequality bounds, so `P` and `A` are constant, as
the fomtools front end requires. Its `param_bounds` are the verified drift box
(`cluster_run.drift_interval`). The back-test is 100 drifted equal-weight
portfolios, `x = (1 + r) / sum(1 + r)` with `r ~ U[-0.15, 0.15]^N`, solved in
order.

## Arms

| arm | what | settings |
|---|---|---|
| `cvxpy_osqp_off` | `problem.solve(solver=OSQP)` | every extra off: `rho=0.1, sigma=1e-6, alpha=1.6` (OSQP's defaults, the same as the fomtools builder), `scaling=0, adaptive_rho=False, polishing=False, warm_starting=False`, 200 iterations, no termination check |
| `cvxpy_osqp_on` | `problem.solve(solver=OSQP)` | OSQP defaults through CVXPY (scaling, adaptive rho) plus `polishing=True`; 200 iterations, no termination check, cold start (`warm_start=False`) |
| `cpg_osqp` | stock CVXPYgen + OSQP | OSQP defaults; runtime `max_iter=200, check_termination=0, warm_start=False` |
| `cpg_fom` | CVXPYgen + fomtools ADMM, translated | `fom="admm"` with the builder defaults (`rho=0.1, sigma=1e-6, alpha=1.6, rho_eq_scale=1e3`), `auto_equilibrate=True` (Ruiz on the canonical QP), 200 iterations, cold start; translation phase only |
| `cpg_fom_opt` | CVXPYgen + fomtools ADMM, optimized | as `cpg_fom`, plus `code_optimization=True` (10-minute budget, `agent_optimize_timeout_s=600`); the optimized solver is kept only if it re-verifies and is benchmarked faster |

Every arm runs exactly 200 iterations from a cold start, with no termination
check, so all do the same number of iterations and differ only in the method's
extras and the code. Warm starting is off everywhere: the holdings are
independent draws, but all lie near the equal-weight portfolio, so starting
from the previous solve would let OSQP skip most of the work.

Stock CVXPYgen is used only through its public API, unmodified:

- **Settings fixed at generation.** CVXPYgen sets OSQP up with its defaults
  (`rho=0.1, sigma=1e-6, alpha=1.6`, scaling on) and exposes no way to change
  rho, sigma, alpha or scaling, or to turn adaptive rho off. Its one arm is
  therefore OSQP's defaults at the fixed iteration count.
- **Adaptive rho carries over between solves in C.** Embedded OSQP adapts rho
  (0.1 → 0.78 on the first N = 10 solve) and keeps the adapted value in the
  solver. CVXPYgen's Python wrapper resets the settings, rho included, before
  every solve; the C interface does not. With a fixed iteration count this
  changes the accuracy reached, not the time per solve.
- **No polishing** in embedded OSQP.

The fomtools arms iterate on the Ruiz-equilibrated canonical QP; the generated
bridge unscales the solution, and `check.py` measures accuracy against Clarabel
on the original problem, so every arm is compared in the original units.

## Running

From `portfolio/`, in the `algoverify` conda env (it has cvxpygen, pip, cmake
and the editable fomtools):

```bash
FOMTOOLS_CODEGEN_AGENT=1 python -m portfolio_cvxpygen.generate   # all N; reuses compiled dirs unless --force
python -m portfolio_cvxpygen.check                               # accuracy of each arm vs Clarabel
python -m portfolio_cvxpygen.benchmark                           # -> results/timings.csv, machine.json
python -m portfolio_cvxpygen.plot                                # -> results/portfolio_cvxpygen_scaling.{pdf,png}, wide CSV
```

Every script takes `--N` (default 10 20 50 100 200). `generate` and
`benchmark` also take `--arms`.

## Output

```
out/                        (untracked)
  cpg_n{N}_osqp/            stock CVXPYgen + OSQP (prefix osqp{N}_)
  cpg_n{N}_fom/             CVXPYgen + fomtools, translated (prefix fom{N}_); fomtools solver in c/solver_code/
  cpg_n{N}_fom_opt/         CVXPYgen + fomtools, optimized (prefix fom_opt{N}_); OPTIMIZATIONS.md in c/solver_code/
  gen_n{N}.json             generation wall times, canonical sizes, which pieces depend on x
  check_n{N}.json           iterations, max |z - z*|, max relative objective gap per arm
  bench_build/              C timing builds and the holdings sequences
results/
  timings.csv               N, arm, level (python | c), us_per_solve, mean_iters, round_spread
  machine.json
  portfolio_cvxpygen_scaling.{pdf,png}, portfolio_cvxpygen_scaling_wide.csv
```

The generated directories have flat names because CVXPYgen imports a code
directory as a module, so the name cannot contain a path separator. Each solver
has its own prefix so that several generated wrappers can be loaded in one
process.

## Timing protocol

- **Rounds.** 7 interleaved rounds per N, each running every arm once. The
  median across rounds of the per-round means is reported.
- **Python level.** `time.perf_counter` around each `problem.solve` call over
  the 100-solve sequence, after 3 warm-up solves. This includes CVXPY's
  canonicalization for the CVXPY arms and the wrapper overhead for the CVXPYgen
  arms.
- **C level.** `bench_c/bench_cpg.c`, built with CMake at `-O3` against each
  generated directory's own source lists, without modifying them. It runs one
  warm-up pass, then 20 timed passes over the sequence. Each solve updates every
  entry of `x`, then calls `cpg_solve()`.

## Solve time to a tolerance, every solver stopping itself

Factor-model sweep (`model.SIZES`, outputs in `out_factor/`, `results_factor/`).
`generate` builds the fomtools solvers with `TerminationKind.OBJECTIVE`: they stop
on OSQP's unscaled residuals at `model.TOL = 1e-4`, checked every
`model.CHECK_TERMINATION = 25` iterations, at most `model.MAX_ITER = 4000`. (The
fixed-iteration `benchmark` and the search-based `tolerance` predate this; the
`fom` arms of `benchmark` now stop at the tolerance too.)

```bash
python -m portfolio_cvxpygen.tolerance_stop    # -> results_factor/timings_stop.csv, out_factor/stop_n{N}.json
python -m portfolio_cvxpygen.scaling_check     # OSQP iterations with Ruiz scaling per draw / nominal / off
```

`tolerance_stop` runs every arm with OSQP's test (`eps_abs = 1e-4`, `eps_rel = 0`,
`scaled_termination = False`, no polishing) and the same ADMM (rho = 1 fixed,
adaptive rho off), and reports per solve the iterations at the stop and
`max(pri_res, dua_res)` there, from the timed runs themselves. Each Python round
of each arm runs in its own process. The CVXPYgen + OSQP Python wrapper resets
OSQP's settings before every solve, so the script fixes rho through `ctypes` on
the wrapper's own extension module (see `fixed_rho_osqp`).
