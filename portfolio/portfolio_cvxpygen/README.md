# Portfolio rebalancing through CVXPYgen: solve time to a tolerance vs. number of assets

The analogue of Fig. 4 of the CVXPYgen paper (Schaller et al.) on our portfolio
rebalancing problem, with the solvers generated by the fomtools CVXPYgen front
end (`fomtools.cvxpygen.generate_solver`, paper §5.3). Every solver stops itself
at the same tolerance. Results: `RESULTS_tolerance_objective.md` at the
repository root.

## Problem

`model.py` is the single definition of the portfolio family, shared with the
standalone verification (`portfolio/problem.py`, which builds the same problem at
a small n and k):

```
minimize  (kappa/2) (||y||^2 + d ||z||^2) - mu' z + lambd ||z - x||_1
s.t.      y = F' z,  1'z = 1,  0 <= z <= z_bar
```

the factor model `Sigma = F F' + d I` written with the exposures `y`, with `F` of
size n x k (`FACTORS` = 100), entries N(0, 1/k), `d = 0.1`, `kappa = 1`,
`lambd = 0.01`, `z_bar = 0.3` (`PROBLEM`). The parameters are the holdings `x`
and the return forecast `mu`:

- `x` is the equal-weight portfolio drifted by one period of returns in
  `[-0.15, 0.15]` (`DRIFT`), `x = (1 + r) / sum(1 + r)`;
- `mu = mu_bar + IC sigma s` (Grinold and Kahn), `mu_bar ~ U[0, 0.5]`, `IC = 0.1`,
  `sigma_i = sqrt(Sigma_ii)`, `s ~ N(0, I)` truncated to `[-3, 3]` (`S_MAX`).

Both enter only `q` and the inequality bounds of the canonical QP, so `P` and `A`
are constant, as the fomtools front end requires. `param_bounds` gives the front
end the drift box for `x` and the truncated forecast box for `mu`. The back-test
is 100 draws of `[x; mu]` per n (`holdings_sequence`), n = 200 / 500 / 1000 / 3000
(`SIZES`), solved in order from a cold start.

## Running

From `portfolio/` with the repository's `.venv` (`UV_NO_SYNC=1`; on macOS pin the
SDK, e.g. `SDKROOT=.../MacOSX26.5.sdk`):

```bash
FOMTOOLS_CODEGEN_AGENT=1 python -m portfolio_cvxpygen.generate --force   # OBJECTIVE solvers, translated + optimized
python -m portfolio_cvxpygen.tolerance_stop --rounds 3 --passes 3         # -> results_factor/timings_stop.csv, out_factor/stop_n{N}.json
python -m portfolio_cvxpygen.plot                                         # -> results_factor/portfolio_cvxpygen_stop_{paper,slides,slides_c}.{pdf,png}, _stop_wide.csv
python -m portfolio_cvxpygen.scaling_check                                # optional: OSQP iterations, Ruiz scaling per draw / nominal / off
python -m portfolio_cvxpygen.rho_sweep                                    # optional: iterations to 1e-4 against rho (how rho = 1 was picked)
python -m portfolio_cvxpygen.profile_codegen                              # optional: wall time of the code-generation stages
```

Every script takes `--N`; `generate` and `tolerance_stop` also take `--arms`.

## Arms

| arm | what |
|---|---|
| `cvxpy_osqp` | `problem.solve(solver=OSQP)` |
| `cpg_osqp` | stock CVXPYgen + OSQP |
| `cpg_fom` | CVXPYgen + fomtools ADMM, translation phase only |
| `cpg_fom_opt` | CVXPYgen + fomtools ADMM, plus the code optimization phase |

The fomtools solvers iterate on the Ruiz-equilibrated canonical QP; the
generated bridge unscales the solution, and the stopping test is on the unscaled
residuals.

**Stopping test.** Every solver stops itself on the unscaled residuals of the
canonical QP, `max(||Ax - clamp(Ax, l, u)||_inf, ||Px + q + A'y||_inf) <= 1e-4`
(`model.TOL`), checked every 25 iterations (`model.CHECK_TERMINATION`, OSQP's
default), at most 4000 (`model.MAX_ITER`). Iteration counts are multiples of 25.

- fomtools: generated with `TerminationKind.OBJECTIVE` at these values.
- OSQP: `eps_abs = 1e-4`, `eps_rel = 0`, `scaled_termination = False`, no
  polishing, and `check_dualgap = False`. OSQP 1.x by default also stops only once
  the duality gap is below `eps_abs`. That test costs 2x to 3.4x more iterations
  at n >= 500 and is not part of the fomtools objective, so it is off. CVXPYgen
  has no setter for it: the C driver writes `solver.settings->check_dualgap`.

**Same ADMM.** `model.ADMM`: rho = 1 fixed, adaptive rho off, sigma = 1e-6,
alpha = 1.6, rho boosted 1e3 on the equality rows, cold start. CVXPYgen generates
OSQP at rho 0.1 and exposes neither rho nor adaptive rho, so
`osqp_update_rho(1.0)` is called once before the first solve. Its Python wrapper
resets the settings to OSQP's defaults before every solve, so
`tolerance_stop.fixed_rho_osqp` writes rho, adaptive rho and `check_dualgap` back
through `ctypes` on the wrapper's own extension module, which is outside
CVXPYgen's public API. C and Python iteration counts agree for every solve, which
confirms the two run the same solver.

## Timing protocol

3 interleaved rounds per n. Each round runs every arm once:
- C, through `bench_c/bench_cpg.c` (built with CMake at `-O3` against each
  generated directory's own source lists) in `stop=` mode: 1 warm-up pass, then
  `--passes` timed passes over the 100 draws; each solve updates every entry of
  `[x; mu]`, then calls `cpg_solve()`;
- Python, through `problem.solve`: 3 warm-up solves, then 1 pass, each in its own
  process (two CVXPYgen wrappers are never loaded into one process).

The reported time is the median of the per-round means. Iterations and
`max(pri_res, dua_res)` at the stop are logged per solve from the same runs. A
7-round, 20-pass run (`timings_stop_7r.csv`, OSQP with its default test) agrees
with this protocol within 1% on the fomtools times.

## Output

```
out_factor/                 (untracked)
  cpg_n{N}_osqp/            stock CVXPYgen + OSQP (prefix osqp{N}_)
  cpg_n{N}_fom/             CVXPYgen + fomtools, translated (prefix fom{N}_)
  cpg_n{N}_fom_opt/         CVXPYgen + fomtools, optimized (prefix fom_opt{N}_); OPTIMIZATIONS.md in c/solver_code/
  gen_n{N}.json             generation wall times, canonical sizes
  stop_n{N}.json            per-solve iterations and residuals
  bench_build/              C timing builds and the draws
results_factor/
  timings_stop.csv          N, arm, level (python | c), us per solve, iterations
  machine_stop.json
  portfolio_cvxpygen_stop_*.{pdf,png}, portfolio_cvxpygen_stop_wide.csv
results/                    archived: the dense-covariance, fixed-200-iteration sweep
                            (N = 10 to 200) behind the paper's current
                            codegen_portfolio_scaling.csv; its scripts (benchmark.py,
                            check.py) are in git history
```

The generated directories have flat names because CVXPYgen imports a code
directory as a module, so the name cannot contain a path separator. Each solver
has its own prefix so that several generated wrappers can be loaded in one
process. The pre-objective solvers and their fixed-200 results are archived in
`out_factor_fixed200_pre_objective/` (untracked).
